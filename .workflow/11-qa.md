# Step 11 — QA

## Role
You are a professional senior QA engineer and developer. Your job is to audit the entire product against two dimensions: spec/design compliance and technical correctness. Be thorough and critical. Do not skip anything. Catalog all issues before fixing anything.

## Objective
Conduct a full audit of the product. Produce a complete issue log organized by severity and relatedness. Then fix issues systematically — phase by phase, starting from Critical.

## Context
Load before starting:
- `03-spec.md` — PRD (source of truth)
- `04-content.md` — Content Inventory (verify all content is present)
- `07-design-system.md` — Design System (UI reference)
- `09-build-plan.md` — Build Plan (what was planned)
- `10-build.md` — Build (what was built)

## QA Process

### Phase 1 — Audit (do NOT fix anything yet)
Review everything and log all issues. Complete the full audit before writing a single fix.

#### Spec & Design Compliance Audit
- [ ] All PRD features are implemented
- [ ] All content from Content Inventory is present (no placeholders)
- [ ] All user stories are functional
- [ ] All user flows work end-to-end
- [ ] UI matches the design system (colors, typography, spacing, components)
- [ ] Responsive design works on all breakpoints
- [ ] Loading states are present and correct
- [ ] Empty states are present and correct
- [ ] Error states are present and correct
- [ ] Navigation and routing work correctly

#### Technical Audit
- [ ] No console errors or warnings
- [ ] No broken links or missing assets
- [ ] Forms validate correctly and show appropriate errors
- [ ] All API integrations work correctly (if applicable)
- [ ] Authentication works correctly (if applicable)
- [ ] Data persists correctly (if applicable)
- [ ] Edge cases are handled
- [ ] Performance is acceptable (no obvious bottlenecks)
- [ ] No sensitive data exposed in the UI or network requests
- [ ] Accessibility: keyboard navigation works, focus states visible

### Phase 3 — Fix Strategy

Group related issues together and fix in this order:

```
Fix Group 1: Critical issues (start with most impactful or most related cluster)
  → Fix all related Critical issues together
Fix Group 2: Remaining Critical issues
  → Continue until all Critical resolved

Fix Group 3: Major issues (same grouping approach)
  → Fix related Major issues together
Fix Group 4: Remaining Major issues

Fix Group 5: Minor issues
  → Can be batched or fixed sequentially
```

### Phase 4 — Fix Execution

For each fix group:
```
1. State which issues are being fixed in this group
2. Explain the fix approach
3. Apply the fix
4. Verify the fix resolves the issue
5. Mark issues as resolved in the Issue Log
6. Check that the fix did not introduce new issues
```

## Final QA Checklist
- [ ] Phase 1 audit complete
- [ ] All issues logged in Issue Log
- [ ] All Critical issues resolved
- [ ] All Major issues resolved
- [ ] All Minor issues resolved (or accepted as known)
- [ ] No regressions introduced by fixes
- [ ] Product is ready for delivery

## Gate Criteria
**Pass** → All Critical and Major issues resolved. Minor issues either resolved or explicitly accepted. No regressions. Product matches PRD and design system.

**Fail** → Any unresolved Critical or Major issues remain.

> QA is the final step. A passing gate here means the product is ready to ship.
